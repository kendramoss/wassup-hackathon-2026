## D1 — Build inside the existing team repo's `backend/` and `frontend/` (15 Oct)
- **Decision:** Origin Proof's Go API lives in `backend/` (Cloud Run service `backend`), the Next.js app in `frontend/` (service `frontend`). The template deploy-agent code there was removed.
- **Alternatives:** new `api/` and `web/` folders as in the build prompt; a fresh `origin-proof` repo as in BUILD-PLAN.md.
- **Why:** CI, Workload Identity Federation deploys, service accounts and IAM (frontend may invoke backend; backend has Vertex AI User) already exist for these two services. New services need IAM changes the CI deployer can't make. The human owner confirmed the template code may be overwritten. The repo's first commit (13 Oct) is after the hackathon start (12 Oct).

## D2 — Health check at `/health`, not `/healthz`
- **Why:** Cloud Run reserves paths ending in `z` and returns 404 for them.

## D3 — Two LLM providers behind `llm.Model`; LiteLLM is development-only (superseded by D49)
- **Superseded (19 Nov 2026, #280):** D49 removed LiteLLM; only `vertex` and `fake` are accepted today. This entry is kept as history. `fake` remains an explicit opt-in for offline UI work and is refused on Cloud Run.
- **Decision (historical):** `LLM_PROVIDER=litellm|vertex|fake`. LiteLLM (OpenAI-compatible proxy) is used now because the team has no Vertex access yet. `config` refuses `litellm` and `fake` when `K_SERVICE` is set, and the deploy workflow sets `LLM_PROVIDER=vertex`.
- **Why (historical):** keeps the research proxy usable for development while guaranteeing the deployed service and official numbers come from Vertex. Every output records `llm_provider` and `model_id`.

## D4 — Real API names differ from the build prompt
- ADK for Go is imported as `google.golang.org/adk` (v1.8.0), not `github.com/google/adk-go`.
- Gen AI SDK: `google.golang.org/genai` v1.74.0 with `Backend: genai.BackendVertexAI`; JSON answers use `ResponseMIMEType: application/json` + `ResponseJsonSchema`; tools use `FunctionDeclaration.ParametersJsonSchema`.
- Gemini 3+ returns thought signatures on function calls that must be sent back unchanged. Vertex: `Part.ThoughtSignature` (carried in `llm.ToolCall.Signature`). LiteLLM encodes the signature into the tool-call `id`, so the ID is passed back unchanged.
- Vertex location defaults to `global` (Gemini 3.x Flash models are not served from `us-central1`, per the repo's earlier README).

## D5 — Temperature 0 and JSON schema on every call
- The research harness used temperature 0 with JSON *mode*. We use a response JSON *schema*, which constrains decoding slightly differently; the Gate B reproduction check (within ~2 points of 89.1%) covers this change.

## D6 — Country normalisation ports `norm()` with one fix
- `domain.NormalizeCountry` reproduces `norm()` from `predict.py` (including its quirks, e.g. "Bosnia And Herzegovina") so eval numbers are comparable. Exception: `norm("Türkiye")` returns "Trkiye" because the regex strips "ü"; we return "Turkey".

## D7 — Triage rule (human decision, 15 Oct)
- Fast path = engine confidence ≥ 0.95 **and** in scope. Scenario cases are **not** excluded. The matching research statistic is "confidence ≥ 0.95 covers 72.4% at 97.8%" (held-out, n=273 of 377); the routed-pipeline "65% at 98.0%" describes a different rule and must not be shown for this one.
- **Amended by D98 (19 Nov, #289):** "in scope" must be established. If a configured scope router fails, scope is unknown and the case goes to review whatever the confidence.

## D8 — Duty rates: sourced for the heat gun, illustrative elsewhere
- Heat gun: China ~41.7% vs Thailand ~16.7% ad valorem (HTS 8419.89.95, classification inferred and unverified for this model; Section 301 List 2 25% is the gap). Sources, dates and caveats in `docs/DUTY-SOURCES.md` (checked 15 Oct 2026). Show the source next to any duty number.
- Other fixtures (LiDAR) keep illustrative placeholder rates; annual volume and group costs are always user inputs labelled "illustrative — editable".

## D9 — CI smoke test without calling the private backend
- The backend accepts only `frontend@`; the CI deployer can't mint a token for it. The deploy smoke test checks the backend's latest revision is Ready and serving all traffic (startup config validation makes a bad config fail here) and that the frontend returns 200. Becomes an end-to-end predict call once the frontend proxies it.

## D10 — BM25 ported exactly, including IDF over the whole corpus
- `retrieval.BM25` mirrors predict.py: tokens `[a-z]{3,}` minus a stop list, first 3,000 characters of facts, k1 1.5, b 0.75, de-duplicated query terms, ties broken by higher corpus index. IDF and average length are computed over the whole corpus (including rulings later than a case); only the candidate set is date-filtered. That leaks term statistics, not text or holdings, and is kept so precedents match the research run.
- Parity on the 377 held-out cases (opt-in `TestResearchParity`): 369 identical precedent lists, 6 same set in another order, 2 with a different 5th precedent. Cause: the labels file gained manual labels after the research run, shifting corpus statistics.

## D11 — Facts splitter port is byte-identical
- `corpus.SplitFacts` reproduces split_facts.py on all 2,790 rulings (`go run ./cmd/corpus compare`), with character offsets handled as runes.

## D12 — Router regime label (new prompt section), dev-validated
- ROUTER.md has no regime check, so router-v1 added a regime label (textile 102.21, USMCA/Part 102, pharma API, substantial transformation, unclear). v1 over-triggered on any Canada/Mexico/USMCA mention (3 of the first 35 dev cases, all decided by CBP under substantial transformation); v2 narrows the USMCA definition. Only dev data was used.
- Measured by `eval scope` on dev: false out-of-scope rate on substantial-transformation rulings, and recall on labelled Part 102 / pharma-API rulings from Jul–Dec 2025. Labels have no separate textile regime (textile rulings fall under part102_tariff_shift).

## D13 — Router runs separately from the engine in eval
- With the router in the loop a dev run took ~45 min (Flash calls are slow through the proxy). The engine run and the router labelling now run separately; `eval report -scope` joins router labels to engine rows to compute the fast path. In the product both run per request.

## D14 — Cited rulings are only rulings shown to the model
- `cited_rulings` = precedents named in the model's reasoning/decisive step/key factor, in retrieval order; ruling numbers the model mentions that it was not shown are dropped. All shown precedents are returned separately as `precedents`.

## D15 — Planner moves operation groups; families are template files
- `planner/templates/*.json` define each family's operation groups (motorised tools & small appliances; LiDAR modules as a second family). Plants carry a capability matrix. The planner enumerates single and double group moves to capable plants in the target country; final assembly is not movable.

## D16 — Facts renderer matches CBP's restatement style (changed after the first heat-gun run)
- First version rendered processing detail for every group. On the 2022 heat gun the engine then predicted Thailand (0.78), though on CBP's own 2022 facts it predicts China (0.78) and CBP held China. The renderer now lists components by country, adds processing detail only for the groups a plan moves (as CBP did in N357771), and the final assembly.
- Consequence: the heat-gun acceptance run is a demo check on a renderer adjusted after seeing that fixture, not an unbiased evaluation. Unbiased planner evaluation needs fresh rulings (finals work).

## D17 — Plans start from CBP's holding on the current setup when the user has one
- Even with the corrected renderer, the engine called the 2022 heat gun Thai (0.78; CBP held China; on CBP's own facts the engine says China at 0.78 — a borderline case). With the wrong starting origin the verifier saw no change and rejected every move.
- A plan request may carry `current_origin` (country + ruling). It sets the starting origin for economics and is stated to the verifier ("CBP has already ruled on variant A: origin China"), the research "A's ruling known" setting (85.5% on 76 pairs). The engine's own baseline prediction is still shown next to CBP's holding. Verifier prompt version `verifier-v1+known-a` when used; dev-evaluated in both modes.

## D18 — Gate D runs on an in-memory store; corpus deployment is an open decision
- `store.Cases` has an in-memory implementation; Firestore drops in behind the same interface once the GCP project is available (SETUP-GCP.md). Cases are lost on restart and not shared between instances until then.
- The server needs the facts corpus (12 MB derived from public CBP rulings) at startup. The deploy builds from `backend/` only and respects `.gitignore`, so the corpus is not in the image. Options for the humans: (a) upload to the GCS bucket and load at startup (needs GCP access); (b) commit the facts files under `backend/data/` (derived public-domain text; the build prompt only rules out committing the 27 MB raw texts); (c) fetch from CROSS at startup (~50 min, not viable). Recommendation: (b) for the hackathon, (a) after.
- **Decided (human, 16 Oct): (b).** `backend/data/` holds `labels.jsonl` and the 2,790 facts files (13 MB); the Dockerfile copies them to `/data` and the server's defaults (`data/labels.jsonl`, `data/facts`) resolve from `backend/` locally and from `/` in the image. `make verify-data` checks the copy.
- Verifier evidence in production comes from live CROSS search with `toDate` (VERIFIER_SEARCH=cross); eval and the demo checks use the local corpus for reproducibility.

## D19 — Duty rates are inputs, not a package
- The build plan listed a `duty` package. Rates are product- and date-specific and the demo needs one sourced product; they are carried as request inputs (`economics.duty_rates` + a source note) and the demo fixture cites `docs/DUTY-SOURCES.md`. A dated HTS lookup can be added behind an interface later.

## D20 — Pasted facts are normalised to the benchmark format; the heat-gun prediction is borderline
- Corpus facts files, and therefore every benchmarked prompt, end with one newline. The API now appends it to pasted facts. Found because the heat-gun demo (CBP's own 2022 facts text) flipped with it: without the newline Thailand 5/5 runs (0.78); with it China 4/5 (0.75–0.85), Thailand 1/5. CBP held China.
- The change restores the evaluated input format; it was not chosen per case. The heat-gun current setup stays a borderline case for the engine: always below the 0.95 fast path (routed to expert review), and the demo should present it that way. Measured 16 Oct, gemini-4-argon via LiteLLM (proxy).

## D21 — Plan display bar stays at 0.95; near misses are shown greyed (human decision, 16 Oct)
- The heat-gun "motor-fan + PCBA" move is precedent-supported on every run (supporting N347421), but the verifier's confidence lands on 0.90 or 0.95, so it was shown in 1 of 3 runs. Dev data (54 pairs) showed every precedent-supported verdict correct at ≥ 0.90 and ≥ 0.95 alike; 0.95 only cuts recall (known-A: 13/46 vs 21/46). Small negative class (8).
- Kept 0.95 as the brief requires. Rejected plans now carry `rejection_kind`; `below_confidence_bar` rows (precedent-supported, confidence below 0.95) sort right after the current setup, and the UI shows them greyed with the label "Precedent-supported — below confidence bar" and their supporting ruling.

## D22 — Accuracy options tried on dev; none adopted (16 Oct)
- Hybrid/embedding retrieval and precedent-order voting were built (kept in code behind flags: `-retrieval`, `-votes`; engine defaults unchanged) and evaluated on dev only. None beat the baseline (eval/RESULTS.md). The configuration is unchanged, so the held-out split was not re-scored.
- Remaining error types need judgment the model lacks, not better retrieval. Family playbooks, the obvious next lever, overfit in research (dev 91.9% → test 88.3%) and are not retried before the deadline.

## D23 — Scoring adjustments: verified, mechanical, applied to every run
- `eval/data/scoring_adjustments.json`: 6 dev exclusions (4 multi-scenario holdings from `eval multiscenario`; H325607, a revocation covering two hose rulings with different origins; N354982, held "the country where the blanks are worked") and 1 alternative gold (N354448, CBP held "Indonesia/Malaysia"). Found by a mechanical scan of both splits (non-country labels, A/B holdings, revocations), each verified against the ruling text. Held-out: one flag (H360070), label correct; no change.
- Six labels the learnability judge called wrong (N353581, N354156, N356481, N350517, H331375, N348376-manual) were checked: CBP's holdings match the labels. The judge, being the same model, disagreed with CBP — not a label problem.
- `NormalizeCountry` keeps "A/B" answers as "A/B" (was glued into one word). Old result rows keep their stored prediction, so N354448 stays wrong in existing runs.
- Effect: dev 90.0% → 90.9% (421/463); held-out unchanged 89.9%.

## D24 — Clarify review: useful questions and conflicts, not an error detector
- `clarify` (clarify-v1, one extra call ~$0.009, only for in-scope cases below 0.95) reports whether an earlier ruling is on point, conflicting comparable rulings with the deciding difference, and up to 3 questions. Triage routes "no precedent on point + questions" to `needs_info`; `POST /v1/cases/{id}/answers` appends answers to the facts and re-analyses.
- Dev (127 below-threshold cases): the flags do **not** separate errors — engine error rate 26% with no precedent on point vs 22% with one; 24% where a conflict was found; needs_info 28% vs needs_review 21% (overlapping CIs). Reviewing the questions by hand, they target the facts CBP relied on (helmet: is the shell moulded to final shape; seamless pipe: are green tubes at final dimensions; filters: does the paper arrive in rolls or cut). Whether answers improve accuracy cannot be measured: the benchmark has no requester answers, and simulating them from ruling text would leak the holding.
- So it ships as broker-facing help, not as a claimed accuracy gain. No held-out run: clarify never changes the predicted origin, and its routing showed no error signal on dev.

## D25 — Cases persist as JSON files; Firestore before deploy (15 Oct)
- `GET /v1/cases` (Cases home page) needs cases to survive a restart. `store.File` writes one JSON file per case to `CASES_DIR` (default `../data/cases`, gitignored), atomically (temp file + rename); IDs are checked against `^[A-Za-z0-9_-]{1,64}$` so a crafted ID cannot escape the directory. `CASES_DIR=off` keeps the in-memory store (D33: an empty value means the default).
- Every write sets `updated_at`; export also records `exported_at`, which drives `step = export`. The list is ordered by `updated_at` descending.
- On Cloud Run the container disk is per-instance and lost on restart, so this is local persistence only. Before deploy, add a Firestore implementation of the same `store.Cases` interface (blocked on GCP setup).

## D26 — Follow-up answers do not settle split votes toward CBP; "unknown" answers stay out of the facts (15 Oct)
- On the 14 dev cases where the engine's 5 votes split between two origins, simulated-requester answers to the clarify questions moved the majority away from CBP more often than toward it (57% → 36% agreement; 1 fixed / 4 broken with "Not stated." lines, 0 / 3 with answered questions only). Small sample, but negative in both variants (eval/RESULTS.md).
- Mechanism: the engine treats "Not stated." and hedged answers as evidence against the processing country, and gives extra weight to facts restated in Q&A form. The simulated requester is also a weak stand-in for a real one: for NY rulings it had no facts beyond the input.
- Product changes: `POST /v1/cases/{id}/answers` keeps "unknown"/"not stated" answers on the case but does not add them to the facts, and refuses a set with no factual answer. Clarify stays broker-facing help (D24); a re-analysis after answers is not claimed to be more CBP-like. Not adopted: re-voting after answers as a confidence signal.
- Follow-up (answers-v2, adopted): `clarify.AppendAnswers` removes hedge sentences from answers and adds a header telling the engine the answers weigh the same as the facts and that unaddressed points are not evidence for any country. On the same 14 cases: 7/14 agree with CBP (0 fixed, 1 broken, vs 1/4 and 0/3 before). The remaining break is a judgment error on factual answers, not a format effect. The engine system prompt (engine-v1) is unchanged, so cases without answers are unaffected. Responses record `prompt_versions.answers`.
- Not tested: answers from real requesters with new facts, which the benchmark cannot supply.

## D27 — Written CBP rules for the confident errors: no gain, not adopted (15 Oct)
- The 12 high-confidence dev errors (96.4% accuracy at ≥ 0.95) split into about 5 real judgment errors (chemical change, preforms, essential character), 4 cases where CBP departed from a closely matching earlier ruling, and 3 scoring or label issues.
- rules-v1 (three short statements of CBP practice, appended to engine-v1) moved dev from 90.9% to 91.1%: 10 fixed, 9 broken, p = 1.0. The rules fixed 2 of the 5 targets and broke cases where CBP weighed other facts. Kept behind the eval flag `-rules`; the product prompt stays engine-v1. No held-out run.
- Conclusion with D22–D26: prompt-level changes do not move accuracy; the remaining confident errors need either examples of CBP's reasoning in training (fine-tuning on Vertex, finals) or human review, which the confidence bar already routes.

## D28 — CBP reasoning with each precedent: no gain, not adopted (15 Oct)
- Showing CBP's application paragraph under each precedent (reasoning-v1) moved dev from 90.9% to 91.4%: 7 fixed, 5 broken, p = 0.77, +13% cost. None of the 9 reviewed confident errors changed.
- With D22–D27, every in-context change tried (more votes, better retrieval, same-family precedents, written rules, precedent reasoning) lands within ±0.5 points on dev. The engine's remaining confident errors are stable judgments that context does not move. Next lever: fine-tuning on Vertex (blocked on GCP setup), with the train split only. Kept behind the eval flag `-reasoning`; the product is unchanged.

## D29 — Scenarios side by side and ruling watch (15 Oct)
- **Scenarios** (`POST /v1/cases/{id}/scenarios`): 1–3 alternative setups per case, each as facts or a structured product, predicted in parallel with the same engine, router and triage as predict. They skip the clarify review (one extra call each, and the question is the comparison) and never change the case's own prediction. Heat-gun demo via LiteLLM (`eval/results/scenarios-watch-heatgun-2022-litellm.json`, proxy): as today Thailand 0.75 (needs review); motor-fan assembly moved to Thailand 0.96 (auto); motor-fan + PCBA 0.98 (auto).
- **Watch** (`POST /v1/cases/{id}/watch`, `POST /v1/watch/run` for a scheduler): re-runs the engine with every precedent dated before today, where the original run only saw rulings dated before the case date. Records status (unchanged/changed), the new prediction and the precedents used that are newer than the case. It does not touch the case's prediction or updated_at, so the cases list order reflects user activity only. Heat gun: unchanged (Thailand 0.78), using N358092 (12 Feb 2026, held Thailand).
- New rulings only reach the pool when the corpus is rebuilt (`cmd/corpus fetch` + `build`); a scheduled rebuild plus `/v1/watch/run` is the deploy-time job (Cloud Scheduler, after the GCP setup). Not evaluated: watch is a product signal, not an accuracy claim.

## D30 — Plan search streams progress; baseline in parallel; concurrency 8 (15 Oct)
- `POST /v1/cases/{id}/plan` with `Accept: text/event-stream` streams the frontend's contract: `start` (every move, so rows draw as queued), `baseline`, `move_started`, `move_done` (the full Plan, economics included: each move waits for the baseline's origin before finishing), then `done` (same body as the JSON response) or `error` {code, message, retryable}, with `: keep-alive` comments every 10 s for Cloud Run. Plain JSON callers are unchanged. Live sample: `eval/results/plan-stream-heatgun-2022-litellm.sse` (proxy).
- The verifier is not deterministic through the proxy: two heat-gun runs today showed 1 plan above the 0.95 bar and then 0 (the 0.90-band plans greyed as below the bar), with the same engine predictions.
- The baseline prediction now runs alongside the moves (they need its facts, not its origin; economics are filled in after the search), and `PLANNER_CONCURRENCY` defaults to 8 (was 4) so the heat gun's 6 moves run in one wave. Heat gun via LiteLLM: 33.4 s → 24.6 s; all moves predicted by 11 s, the rest is the precedent checks (~10–15 s each, in parallel). Results and economics are unchanged (planner tests).

## D31 — Repeatable verdicts (cache), drafts for below-bar plans, CASES_DIR fix (15 Oct)
- Every model call is already at temperature 0, but the verifier's verdict on the same move still varied through the proxy (0.95 then 0.92), flipping the heat-gun Plan screen between "Best plan" and "No plan cleared the bar". `verifier.Cache` stores each verdict on disk, keyed by the task, verifier model and prompt version. A repeated plan search returns the same verdicts (heat gun: 6/6 reused, 29 s → 1 s). `VERIFIER_CACHE_DIR` defaults to `../data/verifier-cache` (gitignored); set `VERIFIER_CACHE_DIR=off` to disable, or delete the directory to re-verify. Plan stats report `verifier_cached`. This is caching, not a fix for the model's variability: the first verdict for a move is still one draw. Not done: majority-of-3 verification (3× verifier cost, ~$0.15 more per search), which would make the first draw steadier.
- `POST /v1/cases/{id}/export` accepts `move_key`: any shown plan, or a rejected plan whose precedent check found support below the bar (`below_confidence_bar`). The draft then states near the top: "Below the confidence bar: Origin Proof's precedent check rated this change 0.92, under its 0.95 bar…". Plans rejected for no precedent, another origin or a failed check return 400.
- Bug fixed: the `CASES_DIR` setting described in D25 was never read by the config loader, so the server kept cases in memory and lost them on restart. Now read (default `../data/cases`) and checked by a config test and a live restart.

## D32 — Auto-accept bar lowered from 0.95 to 0.92 (15 Oct)
- The user chose the lowest confidence at which cumulative accuracy stays at or above 95% on both splits. Proxy, engine-v1: confidence ≥ 0.92 is 95.7% on 81% of dev cases and 96.7% on 80% of held-out cases; with the router's scope check (fast path), 95.1% on 79.1% of dev and 96.6% (93.9–98.2) on 78.5% of held-out. At 0.95 it was 96.4% / 97.8% on ~72%.
- Trade-off: about 8% more cases skip expert review for about 1 point of accuracy; cases scored exactly 0.92 are ~88% right on their own, and the dev lower CI bound is 93.1%. Held-out confirmed the dev choice; it was not used to search for the bar. Re-check on Vertex before quoting official numbers.
- `FAST_PATH_CONFIDENCE` default (`config.DefaultFastPath`) is 0.92; the eval report and summary use it. The plan bar (verifier confidence for showing a plan, `PLAN_CONFIDENCE`) stays 0.95. Eval experiment flags (`clarify -below`, `torn -below`, `-vote-below`) keep 0.95 so recorded runs reproduce.

## D33 — Majority-of-3 precedent check: built, off by default (15 Oct)
- `verifier.NewMajority` runs the check n times in parallel and keeps the majority answer on support (ties against support), with the median confidence of the majority and `verdict.agreement` (e.g. "2/3"). The cache stores the majority verdict under a separate key.
- Two fresh heat-gun plan searches with 3 votes and no cache: 3 of 6 moves gave the same outcome and confidence, one move flipped between below_confidence_bar and no_supporting_precedent, and no plan was shown in either run. Each search took 54–73 s (18 agent runs through the proxy) against ~28 s with one vote.
- So `VERIFIER_VOTES` defaults to 1. The cache (D31) is what makes repeat searches identical; voting adds cost and latency without making the first verdict repeatable. Re-test on Vertex, where variance and rate limits may differ.
- Config: directory settings now take `off` to disable (`CASES_DIR=off`, `VERIFIER_CACHE_DIR=off`); an empty value means the default.

## D34 — BOM import and scenario pricing (15 Oct)
- `POST /v1/products/import` turns a CSV or Excel (.xlsx, first sheet; github.com/xuri/excelize/v2) bill of materials into the structured product: one row per component or operation, header aliases, countries normalised, groups matched to the family template, plants created from the plant column (or the country), capabilities from the groups each plant makes plus an optional `plant_capabilities` column. It returns warnings for what the plan search will lack rather than guessing capabilities. It does not create a case. `backend/testdata/heatgun_bom.csv` imports to the same 6 planner moves as the hand-written heat-gun fixture.
- Scenarios now carry a `comparison` against the current setup from the case's economics (given in the scenarios call, or kept from the last plan search): duty at the predicted origin, duty savings, added cost of the operation groups moved and net, labelled illustrative unless sourced. Heat-gun fixture economics: motor-fan assembly to Thailand saves $500k a year, adds $120k, net $380k. A product scenario that moves no operation group is the current setup: savings and net 0, duty at the current origin's rate, with `origin_differs_from_current` when the engine predicts another origin for it (the heat gun "as today" is predicted Thailand 0.75 while CBP held China). Facts-only scenarios have no moves to compare, so their savings follow the predicted origin.

## D35 — Plan bar lowered to 0.92 to match auto-accept (15 Oct)

## D45 — Rate limits, pinned demo cases, cost on every step (16 Oct)
- Endpoints that call a model are rate-limited per client: light ones (predict, answers, ask, extract, scenarios, watch) 20 a minute, heavy ones (plan, compare-targets) 4 a minute, and a global cap of 120 light units a minute in which a heavy request counts 5 (`RATE_LIGHT_PER_MIN`, `RATE_HEAVY_PER_MIN`, `RATE_GLOBAL_PER_MIN`; 0 turns a limit off). Deployed, the backend is private and only the frontend's proxy calls it, so the proxy must forward the browser's address as `X-Client-IP`; without it every visitor shares one bucket and the global cap is what protects the bill.

Empty: nobody is admin. `make run` and `make demo-seed` use a local default; deployed it must come from Secret Manager (at least 16 characters).
- `DELETE /v1/cases/{id}` and `PUT /v1/cases/{id}/pin`. Pinned cases list first and survive visitors on the shared Firestore store. The demo seed pins the cases it creates and sends `ID_TOKEN` as the identity token for a private Cloud Run service.

## D65 — Live MFN rates for HTS lines outside the sourced table (17 Oct)
- The duty table (D52) covers two researched lines (8419.89.95, 9015.80.20). Any other product with an `hts` got no rates, so its plan showed no duty effect until the user typed every rate in.
- With `DUTY_LIVE_MFN=on`, a subheading the table does not have gets its MFN (column 1 general) rate from the USITC HTS REST search (`https://hts.usitc.gov/reststop/search?keyword=<NNNN.NN.NN>`, inspected 17 Oct: a JSON array of rows with `htsno`, `description`, `general`). The search is fuzzy (0402.21.25 also returns 2106.90.03), so only rows with the same 8 digits count. The rate is on the 8-digit row, or on its only 10-digit row (8471.30.01.00); statistical lines with different rates, or no rate printed, give no rate. Only plain ad valorem rates are parsed ("4.2%" = 0.042, "Free" = 0). Specific and compound rates ("4.4¢/kg", "20.7¢/kg + 7.5%") come back as printed with `supported: false` and are never converted.
- The table always wins. A live rate never includes Section 301, forced-labor or 232 duties, or special (FTA/GSP) rates; it is marked `mfn_only` with its source URL and `fetched_at`, and every note says "additional duties (Section 301, forced-labor, 232) not included — check before relying on the total". No 301 rate is guessed. Column 2 origins (Cuba, North Korea, Russia, Belarus) are never filled. Nor is the United States (or Puerto Rico, inside the US customs territory): a US plant, US current origin or reshoring target to the US is not imported, so giving it the MFN import rate would put a false duty into the plan's duty effect, net and savings. It stays unpriced unless the user gives a rate, and on its own never triggers an HTS fetch.
- `GET /v1/duty-rates?hts=` answers such a line as `{hts, description, live_mfn}`. A fetch (not a cached answer) counts against the per-client lookup limit (D58), so enumerating subheadings cannot get our user agent blocked. Plan, scenarios and compare-targets fill the MFN rate for the case's countries the user gave no rate for (plants, components, current and predicted origin, target or scenario origins) and list them in `economics.duty_rates_live_mfn`. They ask the HTS only when an origin is missing a rate. Like table rates, live rates are not stored on the case. `economics_priced` on GET case uses only rates already cached, so viewing a case never waits on the HTS.

Answers and missing lines are cached in memory for `DUTY_LIVE_MFN_TTL` (default 24 h). A failed fetch is cached for 1 minute, so an outage does not cost every plan search a timeout. A request the caller cancelled is not cached. Failure means no rate (404 on the endpoint, rates left as given in a plan), never an error. At most 2,000 subheadings are cached.
- Measured (live, 17 Oct): the HTS gives 8419.89.95 as 4.2%, the same MFN component as `rates.json`. 6505.00.90 comes back as unsupported compound "20.7¢/kg + 7.5%". No accuracy number applies: this is a lookup, not a prediction.

## D68 — Sign-in and team workspaces, backend half (17 Oct)
- **Problem:** visitors are anonymous (D58: a hashed `X-Visitor-ID` per browser), so a trade-compliance team cannot share cases, and a user loses their cases on another device. History does not say who took a step.
- **What it does:** with `TEAMS=on`, the frontend proxy forwards the user's Google ID token as `X-User-Token`. The backend verifies it with `idtoken.Validate` (signature against Google's keys, expiry, audience `TEAMS_AUDIENCE`, issuer `accounts.google.com`, `email_verified`) behind a `teams.Verifier` interface, so tests use a fake. A bad or expired token is 401 `unauthenticated` everywhere (not a silent fall-back to anonymous, which would file the user's cases outside their workspace). Workspaces (`id`, `name`, `members`, `invited`, `created_by`) live in Firestore next to the cases (`workspaces`, plus `workspace_members/<email>` so a user is in at most one workspace and the lookup is one read), in memory locally. Endpoints: `POST /v1/workspaces` (the caller becomes admin), `GET /v1/workspaces/mine` (workspace plus pending invitations), `POST /v1/workspaces/{id}/members` (admin only; 404 for a workspace the caller is not in), `POST /v1/workspaces/{id}/join`. Adding a member is an invitation (an `invited` list on the workspace document; no `workspace_members` document): the invitee is not a member, and their cases stay personal, until they sign in and call `join` with their own token, which in one transaction checks the invitation and that they are in no workspace. So an admin cannot pull someone into a workspace, read the cases they create, or pre-claim a company's addresses to stop its real team forming (review finding: before this, adding an email made it a member at once, and the victim could neither leave nor create their own). Inviting does not check whether the email is already in another workspace, so the answer does not reveal it; joining a second workspace is 409. Members plus invitations are capped at 50. A signed-in user's case stores a hash of their email as `owner` and their workspace ID as `workspace` (a Firestore field, queried so workspace cases are never pushed out of the 200-case list cap). A signed-in user sees the pinned demos, their own cases, their workspace's cases and the anonymous cases from the same browser; everyone else gets 404, anonymous visitors included, whatever `CASE_OWNERSHIP` says. History events record `actor` (the email). Anonymous requests keep D58 exactly.
- **Turn it on:** create an OAuth client ID (Web) in the GCP project, set `TEAMS=on TEAMS_AUDIENCE=<client id>.apps.googleusercontent.com` (config refuses `TEAMS=on` without one: an empty audience would accept any app's Google token), then ship the frontend half (`docs/issues/frontend-teams.md`). With `TEAMS=off` (default) the routes are not registered, `X-User-Token` is ignored and nothing changes.
- **Measured:** nothing model-related (no model calls). Tests: verifier claims table (issuer, audience, unverified email, malformed token), workspace store rules, and invite and join rules (invitation is not membership, uninvited join 404, joining a second workspace 409, invitations count toward the cap), an invited-but-not-joined victim whose cases stay hidden from the inviter and who can still start their own workspace, cases from before joining staying personal, and a visibility matrix of 9 viewers × 8 cases (list and GET) with `CASE_OWNERSHIP` off and on, outsiders 404 on every case endpoint, actors in history, teams off unchanged. Smoke-tested locally on :8208 with the fake model: startup, 401 for a token with the wrong audience, anonymous list 200.
- **Not done:** the frontend (sign-in button, forwarding the token); declining or revoking an invitation (a stale one is harmless: it grants nothing until accepted), removing members, leaving or deleting a workspace, renaming it, transferring admin, invitations by link; moving existing anonymous cases into a workspace; a user in several workspaces; per-user rate limits (still per IP). The Firestore workspace store is covered by the emulator test only, which was not run here (no gcloud on this laptop). An email removed from a Google Workspace domain keeps access until removed from the workspace (not possible yet).

## D69 — API keys with daily quotas for brokers (17 Oct)
- Brokers want to call the API from their own systems, but the API only knew browser visitors: limits keyed on `X-Client-IP`, cases owned by the frontend's `X-Visitor-ID` (D58). A broker's server has one address shared by many users, no visitor cookie, and no way to be stopped short of blocking the address.
- **Keys.** `POST /v1/admin/api-keys {name, daily_quota}` (admin token) returns a key once: `op_` plus 32 random bytes in base64url. Only its SHA-256 is stored, with name, `created_at`, `daily_quota` and `disabled`; the key ID is the first 16 hex characters of the hash, so a check is one read by ID and a constant-time comparison of the full hash. `GET` lists keys without secrets; `DELETE /v1/admin/api-keys/{id}` disables a key for good (it stays in the list). Stored in Firestore (`api_keys`; per-day counts in `api_key_usage/<id>_<date>`, transactional increment shared by all instances) when cases are there, else in memory.
- **Requests with `X-API-Key`.** Every `/v1` request with the header is checked first: unknown, malformed or disabled is 401 `unauthorized` (never a silent fall back to anonymous). Each request counts against the key's quota for the UTC day; over it, 429 `quota_exceeded` with `Retry-After` at the next UTC midnight. A key gets its own light/heavy/lookup buckets instead of the `X-Client-IP` ones (same sizes as a visitor's), and still takes from the global bucket and the daily spend cap (D59): the cap refuses keys like everyone else. Cases created with a key store a hash of the key ID as owner (the D58 field, prefixed `key_`); a key sees the pinned demos and its own cases only, and its cases are a 404 for visitors and other keys even with `CASE_OWNERSHIP` off. The admin token still sees everything. Requests without the header behave exactly as before.
- **Turn on:** `API_KEYS=on` (default off; needs `ADMIN_TOKEN`, and `CASES_STORE=firestore` on Cloud Run so keys survive restarts and are shared). Off, the header is ignored and the admin endpoints are 404, so merging changes nothing in production. Documented in `openapi.yaml` (securitySchemes `ApiKey` and `AdminToken`).
- **Measured:** tests only (`internal/apikey`, `internal/httpapi/apikeys_test.go`: issue/list/disable, 401, quota and reset at UTC midnight, per-key buckets that follow the key across addresses, spend cap, ownership both ways with ownership off; config validation). A local run on port 8209 with the fake model issued a key and got 200, 200, 429 `quota_exceeded` with `Retry-After`, and 401 for a bad key. The Firestore store has an emulator test that skips without `FIRESTORE_EMULATOR_HOST`; it was not run here (no emulator on this laptop).
- **Not done:** the backend is private on Cloud Run (only the frontend may invoke it), so brokers cannot reach it yet: the frontend proxy does not forward `X-API-Key`, and a public route (or opening the backend with its own ingress rules) is a separate decision. Quotas count every request including reads and 4xx answers, and a request is counted before its rate limit is checked; there are no per-key rate sizes, no key expiry or rotation, no usage endpoint, and no UI for keys. If the usage counter is unavailable the request is served (and logged) rather than refused. A disabled key's cases stay owned by it, visible to the admin only.

## D70 — Rate limits shared across instances, off by default (17 Oct)
- **Changed by D137 (21 Nov):** on Cloud Run an unset `RATE_LIMIT_STORE` now means `firestore`.
- The rate limits (D45, D57, D58) are token buckets in each instance's memory, so with up to 3 Cloud Run instances a client gets about 3× its limit and the global cap is about 3× too (D57, D59). The spend cap (D59) bounds the bill but not how fast one client can use it.
- `RATE_LIMIT_STORE=firestore` counts the same classes and limits (light 20, heavy 4, global 120 in light units with heavy = 5 and a batch = 20 and the whole heavy burst, lookups 30 outside the global cap) in fixed one-minute windows shared by every instance. Each counter is a document in `rate_limits` (`<sha256 of client key, 24 hex>-<class>-<window start>`, and `global-<window start>`) with `n` and `expires_at` (the window's end). One request is one Firestore Commit that increments its client counter and the global counter together and returns both new totals (the low-level API, since only a raw Commit returns increment results). Over a limit, the request takes its increments back with a second write, so a refusal uses nothing, and gets 429 `rate_limited` with `Retry-After` until the window ends. A counter seen full is refused without a store write for up to 10 s. Same admin bypass, same `X-Client-IP` keying with IPv6 grouped by /64; addresses are stored only as hashes. The Commit has a 1 s timeout and no automatic retries (a retried increment could count a request twice).
- Fail open: if the store errors, the request falls back to this instance's buckets (the current limiter, still limited) and a warning is logged at most once a minute per instance.
- How to turn it on: `RATE_LIMIT_STORE=firestore` (needs `GOOGLE_CLOUD_PROJECT`; uses `FIRESTORE_DATABASE`). `local` (default) keeps today's per-instance buckets, so merging changes nothing in production. `memory` runs the shared limiter in one process, for trying it locally. Before turning it on, add a Firestore TTL policy on `rate_limits.expires_at` so ended windows are deleted (`gcloud firestore fields ttls update expires_at --collection-group=rate_limits --enable-ttl`); without it the documents stay (a few hundred bytes each).
- Measured: unit tests only. Two limiters on one in-memory store enforce one combined limit for each class (light, heavy, lookup, global in heavy units, batch); a refused heavy request leaves the global count unchanged; window rollover; a full client costs no store write; two HTTP servers on one store share a client's limit with 429 and Retry-After; with the store failing, requests fall back to the local limit (201, 201, 429) and the outage is logged once. The Firestore path is tested against a fake gRPC Firestore server (one Commit per request, mask `expires_at` only, increment on `n`, no retry on error); an emulator test (`FIRESTORE_EMULATOR_HOST`) is written but was not run here (no emulator on this laptop). Smoke-tested locally on port 8210 with `RATE_LIMIT_STORE=memory`: third request in the minute returned 429 with `Retry-After`. Latency on real Firestore was not measured.
- Not done: no staging run on Firestore, no TTL policy created, no `deploy.yml` change. A fixed window allows up to twice a limit across a minute boundary, which the token buckets did not; a sliding window would cost a second read. Every limited request writes the single `global-<minute>` document, which Firestore sustains at about one write a second per document before contention; at the configured 120 light units a minute that is within reach, but a sharded global counter would be needed for much more traffic. The spend meter (D59) still reads its total on every request; that read was not merged into this write.

## D97 — A plan, comparison or export built from superseded case inputs is refused (19 Nov, #287)
- **Problem:** a plan search, SSE plan search or country comparison that started before a new BOM was applied could finish afterwards and attach a result for the old product to the new one. A chosen-plan export could combine old plan facts with the new product.
- **Decision:** before the work starts, the handler takes a fingerprint of the case inputs (product, facts, excluded rulings, current origin, family, date; an empty and a missing exclusion list count as the same). The save runs in the store update and refuses when the latest case no longer matches. A chosen-plan export also checks that the stored plan search it was chosen from is unchanged. Money, chat and history are not part of the fingerprint.
- **Result:** the request fails with 409 `conflict` and saves nothing. On the plan event stream the same failure is an `error` event with `retryable: true`. The caller runs it again.
- **Watch re-check:** the same check guards a watch result (`POST /v1/cases/{id}/watch` and the scheduler run), because a new BOM or answers clear the watch. A superseded re-check is a 409 and, in the scheduler run, counts as failed.
- **Export in the UI:** Download and Print record the export, and the recording call answers with the letter as the case stands now. The Draft screen compares it with the previewed letter of the same format (raw content, before the requester's own fields are filled in) and lets the letter out only when they match. Anything else holds it back: a 409, a different letter, a chosen move or plan that no longer exists, an authorization failure, a 4xx or 5xx, a network failure, or a success with no letter. The error shows with the server's own message (Retry only where the error is retryable), the stale draft is dropped, and nothing is downloaded or printed. There is no fail-open path: a letter whose freshness cannot be verified is not released, so a transient recording error costs a retry.
- **Answers (#288):** the answers handler uses the same check, so answers worked out against superseded inputs get 409 `conflict` and are not saved. When accepted answers add facts, the plan search, target comparison, watch result and export mark are cleared (the same clear as applying a BOM); history and the user's scenarios stay.

## D98 — A failed scope router sends the case to review, never to auto-accept (19 Nov, #289)
- **Problem:** when a configured scope router errored, the case was treated as in scope. A textile, pharmaceutical or Part 102 case with a high-confidence general answer could be auto-accepted, although nothing had established which legal regime applied (D7 needs confidence and scope).
- **Decision:** scope is now three-valued in practice: confirmed in scope, out of scope, or unavailable. When a router is configured and fails, the case keeps its provisional prediction, the route is `needs_review`, and the reason is exactly: `scope unavailable: the scope router failed, so the legal regime is not confirmed; an expert reviews`. Specialist engines, the global and per-family auto bars, and the fallback fast path do not apply, and the follow-up questions step is skipped. The case is not described as out of scope.
- **Unchanged:** with no router configured (a deployment choice, not a failure) triage behaves as before. A working router behaves as before.
- **Not measured:** how often the router fails in production; this is a safety rule, not a calibrated one.

## D99 — Case-insensitive upload media types, and no empty success on bad money (19 Nov, #324/#325)
- **Multipart dispatch:** the batch, product-import and BOM-version endpoints parse the media type and compare it case-insensitively (`mime.ParseMediaType` with `strings.EqualFold`) instead of a case-sensitive prefix check. Media types and subtypes are case-insensitive (RFC 9110), while the boundary parameter keeps its casing. A malformed or unsupported type falls through to the JSON body path, which returns a coherent error; browsers' lowercase `FormData` uploads are unchanged.
- **Money import:** `amount` rejects NaN and Inf, and derived products and sums that overflow are skipped with a warning. Invalid cells keep the existing "warn and ignore" contract rather than failing the whole import.

## D100 — A selected specialist is judged on its own; failure, missing label and unknown regime are explicit review states (19 Nov, #304 #300 #294 #319 #303)
- **Problem:** a healthy specialist (textile 102.21, Part 102 marking, pharmaceutical) failed whenever the unused general engine failed. A specialist error fell through to an ordinary triage as "out of scope", family confidence bars could override fallback-model review (D63 left bars off by default), the watch re-ran the general engine on specialist cases, Ask what-ifs bypassed the dispatch saved scenarios use, and a broker draft asked the substantial-transformation question under every non-textile regime.
- **Decision:** one dispatch and one triage policy (`httpapi/dispatch.go`) serve classify, scenarios, the watch and Ask. A selected, enabled specialist is called first and does not need the general engine to succeed. If it fails and the general engine succeeded, the general result is kept only as provisional and the route is `needs_review` with a reason naming the regime (`specialist unavailable: the <regime> engine failed, so the legal regime is not applied and the prediction is a provisional general one; an expert reviews`); if both fail the request fails. A confirmed special regime with no enabled engine stays an out-of-scope review.
- **Scope states:** `no_router` (a deployment choice, unchanged), `configured_failed` (D98, `ScopeUnavailableReason`), `confirmed`, and `label_missing` (a stored case with no scope label: `LabelMissingReason`, always `needs_review`, never auto). `configured_failed` and `label_missing` both mean scope is unavailable but stay distinct structured states.
- **Fallback before family bars:** a fallback-model answer is judged by the fallback policy before any family bar, so a family bar cannot auto-accept it. Family bars stay off by default.
- **Actual regime:** the regime that produced a stored prediction is read from its trace prompt version (`PredictionRegime`). It is `""` (unknown) for an unrecognised version, and consumers treat that as unknown, never as the router label and never as general. Export drafts and saved what-ifs use it.
- **Export:** the draft is written under the actual regime in both formats; unknown or legacy predictions render the general wording with a review note outside the printable letter that the framework is not confirmed.
- **Ask:** a what-if carries regime, specialist state, scope, route, reason and a provisional note, and these are saved with the chat turn; a saved what-if with no recorded regime reads as `unknown` and provisional.
- **Not measured / not validated:** how often a specialist or router fails in production, answer quality on real models (the prompt snapshot was updated offline, no model calls; D72 regression needs separate approval), and the legal text of the new drafts, which a broker must review.

## D101 — The ruling watch stays on the case's own regime and never reports a method change as a ruling change (19 Nov, #294)
- **Problem:** the re-check ran the general engine on every case, so a Part 102, textile or pharmaceutical case could come back with another origin and be reported as changed by today's rulings, although the legal test had changed.
- **Decision:** the re-check pins the case's stored scope label and uses the same dispatch and triage as a new case (D100); it does not route again. Each result records a `basis`: `precedent` (same regime and method; any change is the rulings), `regime` (another regime's engine answered), `method` (same regime, another engine version), `specialist_unavailable` (the stored regime's engine failed; the general answer is provisional) or `unverified` (no stored label, or the original regime is unknown, so the two are not comparable). It also records the regime that answered, the case's original regime, scope, specialist state and the triage of the result. `status` stays the origin comparison. The D97 check still decides whether the result may be saved (409 when the inputs moved).
- **Consumers:** only `basis: precedent` is a change caused by new rulings. The scheduler's `changed` list can include method and regime differences, so a consumer must read `changed_basis` (case id to basis) and not alert on a ruling change for any other basis. A result saved before this carries no basis and so cannot say whether the rulings moved or not: it is read as unknown, and the screens show "Re-check needed" (never Changed or Unchanged) until the case is re-checked; nothing is deleted or migrated.
- **Screens:** a watch result whose basis is not `precedent`, or whose triage is `needs_review`, shows as "Needs review", never as Changed or Unchanged by today's rulings. This is deliberate: when the basis or the triage is uncertain, the screen does not give legal assurance in either direction, and the cost is that more cases show as needing review than the old general watch label did. A reviewer objected that a `precedent` basis with `needs_review` triage would be better kept as "Unchanged"; the ruling is to keep it as review.
- **Reasons shown:** a Needs review watch gives the reason for its basis in words (a different regime, a different engine version, a failed specialist, an unconfirmed regime). The triage reason is added only when its route is a review route; an approving reason such as "confidence 0.97 >= 0.92 and in scope" is never shown beside Needs review.
- **Changed and review together:** a genuine precedent change stays labelled "Changed". When the watch result's triage route is a review route, the case page adds that a person must also look, with the reason; an approving reason is never shown. Every state that needs a person (Changed, Needs review, Re-check needed) is styled as needing attention in the list; only a plain Unchanged is styled as quiet.
- **Ask what-ifs (D100):** an Ask what-if card shows the auto-accept ruler only when its regime is known, its route is auto and it carries no provisional note. Otherwise it says Needs review, Needs more facts or Provisional answer, names the regime in words and gives the reason, and a scenario saved from it carries a warning that it is re-run under the full policy.
- **Not measured:** how many cases the watch will send to review in production.

## D103 — A visitor's scroll interrupts the figure arrival replay (19 Nov, #334)

## D105 — Supplier identity is separate from the plant ID slug; money import uses the product's resolved IDs (19 Nov, #302 #323)

- **Limits:** an ID can depend on the other names in the same sheet (a colliding new name changes both IDs), so costs are valid only against the product from the same sheet. No route carries money costs through `KeepPlantIDs` today; the pairing would need a remap if one is added.

## D108 — One strict HTS syntax before any sourced, live or automatic pricing (19 Nov, #306)
- **Decision:** `duty.ParseHTS` accepts 8 digits, or 10 with a statistical suffix, with one consistent separator (dot, space or dash). Anything else (letters, other lengths, mixed separators) is invalid. With duplicate `hts` parameters the first wins. A malformed HTS makes no network call and fills no rate; money prefill reports it in `hts_note`.
- **Why:** letters around a known number, or an overlength string, used to return researched rates and auto-fill economics.

## D109 — Section 301 exclusion applicability is judged at one current UTC instant per request (19 Nov, #305)

## D111 — Verifier support needs validated, directly retrieved rulings; cached verdicts replay only with current proof (20 Nov, #295)
- **Decision:** eligible support is limited to rulings the agent retrieved directly: search hits and read results whose header names the requested id, dated before the case bound and not excluded. A ruling mentioned only in another ruling's text is never eligible, and the exclusions are checked again when the answer is accepted. A supported verdict needs a supporting ruling. - **Cost:** every cached verdict that cites a ruling, seeded demo verdicts included, misses once and is re-run. `ValidationEpoch` is a validation tag, not a prompt version; the `verifier-vN` names are unchanged because the prompts did not change.
- **Limits:** a counter ruling is checked through the panel's proofs only; `ProofFor` is exported for fixtures.

## D112 — A claimed origin change needs distinct, known, well-formed origins (20 Nov, #297)
- **Decision:** a verdict is supported only if both origins are usable and different. Each answer origin is checked as raw text before normalisation: an empty origin, an empty or "unknown" member (`Unknown/China`, `China/`, `A//B`) or any comma makes it unusable, so it is never read as the one country left over. Usable origins go through the domain country rules and are compared as sets: equivalent origins (USA and United States of America, PRC and China, Viet Nam and Vietnam, Thai and Thailand, Burma and Myanmar) are not a change. When a known baseline for variant A is given, `origin_a` must equal it, and a baseline that is set but unusable fails closed instead of being skipped. The ruling citation stays as validated; only the supported flag is cleared. The same check runs on fresh answers and on every cached replay. `ValidationEpoch` becomes `val2`.
- **Why:** an answer with the same country on both sides and `changes_origin=true` was marked precedent-supported, and equivalent spellings or a half-unknown origin could pass as a change.
- **Cost:** every cached `val1` verdict that cites a ruling misses once and is re-run; no prompt or model version changed. Two aliases (`thai`, `burma`) were added to the domain country table, nothing more.
- **Limits:** a comma anywhere makes an origin unusable, so a country name that contains a comma and is not in the alias table (for example "Korea, Republic of") leaves a verdict, or a known baseline, unsupported: a possible false negative, chosen over a guess. Set comparison is strict (Thailand/China differs from Thailand; a baseline of China contradicts China/Thailand). The cache sees only normalised stored origins, so it relies on the fresh check never storing a supported verdict with a malformed raw origin; entries from before this check are `val1` and miss.

## D113 — The engine prediction cache keys on the evidence revision (20 Nov, #316)

## D114 — Corpus rebuild and bundle reconcile only what they generated (20 Nov, #317)
- **Decision:** `build` and `bundle` record the ids they wrote in a manifest (`.generated_manifest.json`, `.bundle_manifest.json`) and remove only obsolete `<id>.txt` files from the previous manifest, never by glob and never recursively, after checking each is a regular file. ## D115 — A clarification sentence that mixes a fact with something unknown is kept whole (20 Nov, #318)
- **Decision:** for the re-analysis, a sentence that states an independent fact and also something unknown is passed on whole and verbatim, qualifiers included. Sentences that are only unknown, conditional, hedged, elided or built on a relative or wh-clause are left out whole. No clause is ever cut out, because a cut can turn a qualified claim into a certain one.
- **Why:** "The motor is made in Thailand, but its value share is unknown" lost the motor; earlier attempts to keep only the known clause kept producing false certainty ("…, but the accuracy of this is unclear").
- **Cost:** the model reads more uncertainty text, and some legitimate mixed answers are dropped whole. `answers-v2` is unchanged.

## D116 — Ask can read every accepted fact; what-if uses one canonical facts string (20 Nov, #320, #321)

Limits are unchanged: 6 tool calls, 6 history turns, 2 what-ifs.

## D117 — Every model attempt is metered once, at the raw client, and reported usage is charged even when the answer is unusable (20 Nov, #312)

## D119 — The case list is scoped to the caller before the recent-case cap (20 Nov, #301)

Foreign activity can no longer push an authorized case out of the window. Admin keeps the global window, widened until it holds the cap of real cases.
- **Legacy documents:** Firestore cannot query a field a document lacks, so the owner and pinned listings read every case document, decode the stored case, and filter on the decoded `Owner` and `Pinned`. No migration, backfill or index is required for correctness, and a stale top-level pinned flag cannot expose a case that is not pinned.
- **Cost, stated plainly:** these listings are not database-scoped. A signed-in user's list does one full-collection read for pinned cases and two for owner cases (three in total), a visitor or broker key two, plus the workspace query; the cost grows with the whole collection until a separate migration writes the fields and lets the reads become queries. Corrupt documents are skipped.
- **Why:** the global window was filled by other principals' activity.

## D120 — A pinned demo keeps the visitor's own Ask conversation without storing it (20 Nov, #309)
- **Decision:** `POST /v1/cases/{id}/ask` accepts an optional `history` of at most 6 completed `{question, answer}` turns (question 2000 characters, answer 4000, both non-empty). It is used only on a read-only pinned demo and is ignored on every other case, where the saved chat is the only source. It is never stored. The agent sees the seeded demo chat followed by the visitor's turns, cut to the last 6, and the answer-memo key covers exactly that history, so different conversations never share an answer. More than 6 turns, or an over-long entry, is a 400.
- **Long answers:** the browser replaces an entire answer over 4000 characters with a fixed omission marker in the context it sends, keeps the question, keeps the original answer on screen and tells the visitor the answer was left out of the context. The agent loses that answer's content; the visitor can restate it. Nothing is truncated to a prefix and nothing is summarized.
- **Which turns are the visitor's:** the browser remembers them per tab and per case in `sessionStorage` (`op:ask-own:<case>`), as a marker for each successful completed turn (its timestamp and the first 80 characters of the question), bounded to the last 6. Seeded, pending and failed turns are never marked, a marker from another case is not used, and Reset clears them, so a full page reload keeps the conversation context. If storage is unavailable the ask simply sends no history. The markers are never sent to the server.
- **Why:** the drawer showed the visitor's earlier turns, but the next request gave the agent only the seeded chat, so dependent follow-ups lost context.

## D130 — A model's configured identity is tracked apart from the version the provider reports (20 Nov, #344)
- **Decision:** a trace carries `requested_model`, the configured model the call was made to (the primary or the fallback), alongside `model_id`, the version the provider reported, which may differ (alias `gemini-4-argon`, version `gemini-4-argon-001`). `Trace.Identity()` is `requested_model`, or `model_id` on traces recorded before the field existed. `model_id` keeps its meaning as the diagnostic.
- **Cache and triage:** the prediction cache stores and reads under the requested identity, so a primary answer replays whatever version the provider reported, and `triage.AnsweredByFallback` compares the requested identity with the configured primary. A genuine fallback answer is stored under the fallback's key and never satisfies a primary lookup, so a later primary success is not blocked (D56). Entries written before the field existed are read as the primary's.
- **Unchanged:** spend prices the model that answered, from the reported version, below the cache and the fallback (D104); a cache hit costs nothing.
- **Known limit:** when votes are mixed, the winning vote's trace decides the identity, so a primary vote that wins over fallback votes is cached and triaged as primary.
- **API:** `requested_model` is an optional string in `prediction.trace`, which the schema leaves an open object, so `openapi.yaml` and the generated types do not change.
- **Why:** a successful primary response with a version suffix was treated as a fallback answer: it forced review with a false reason and was never replayed from the cache.

## D131 — A scenario comparison is only shown against the inputs it was priced with (20 Nov, #288, #347)
- **Decision:** each saved scenario comparison carries a basis stamp: a hash of what it was priced against, namely the case's product, facts, answers, current origin (CBP's if known, else the prediction), family, date and excluded rulings, plus the money the planner prices with (import value, duty rates, group costs). A comparison whose stamp differs from the case's current basis is recomputed from the stored predictions (cached tariff rates only, no model call) when the case is read, never shown stale. Reading does not write the store.
- **Scenario definitions stay:** a new BOM, new answers or new money clear or reprice the derived comparison, moved groups and `origin_differs_from_current`, but never the scenario's label, facts, product or prediction (D97's "scenarios are the user's own setups" holds). `clearDerived` drops the comparisons with the plan and targets.
- **Money:** `PUT /v1/cases/{id}/economics` reprices and restamps the saved scenarios in the same update as the economics, and returns them as `scenarios` (absent when there are none). A scenario save that was priced against superseded inputs, including the money, is discarded with a 409 (the guard runs before the economics are assigned), so it cannot restore stale numbers.
- **Missing inputs are null, not zero:** with no annual import value, or a duty rate or cost that is missing, the comparison is `null` and the screen shows "add duty rates or costs". There is no stale flag.
- **Browser:** when the browser cannot re-read the case after saving money, it uses the `scenarios` from the PUT response instead of keeping the old ones.
- **Cold live-rate cache:** a read or a money save reprices from the researched table, rates the user gave, and live tariff rates already in the cache; it never fetches a live rate and never keeps an old comparison. When a scenario needs a live rate that is not cached (no table line for its tariff code, and no rate given for that origin), its comparison is `null` ("add duty rates or costs"), not an old or invented number. This applies to every money edit and every baseline change, not only to scenarios saved before the stamp existed, and the comparison can stay `null` until the scenarios are run again, which prices them with live rates. Rates the user gave are never affected.
- **Why:** after a BOM change or a money edit the case still showed savings, moved groups and a changed-origin flag worked out from the old inputs, for example $380,000 after the inputs implied $880,000.

## D136 — Optional operating-cost model: modelled net, explicit inputs, cost only demotes (20 Nov, #281)
- **Decision:** a request may carry `economics.operations`. When it is active, plans, the country comparison and scenarios use one shared calculation (`backend/internal/planner/opcost`): modelled net per year = duty saved − operating cost difference − one-time costs spread over a user-chosen horizon. Without an active block every path, response and stored case is as before.
- **Inputs:** the user types every figure; none is defaulted or estimated. An empty field is not entered, an explicit 0 is a known zero. Labour and logistics need an explicit `included` or `additional` basis to avoid double counting. Capex and retooling count at the destination plant only; capital at the current plant is sunk and ignored. Horizon is required whenever a one-time cost applies.
- **Results:** an unknown amount is `null`, never 0, and makes only the affected total unknown. A factor not entered is not modelled and is listed. `not_modelled` is returned with every result, also a fully priced one, and clients must show it beside a priced figure (the API contract; this decision does not claim any screen does). "Best" means the best of the searched moves under the inputs supplied, not a global optimum.
- **Feasibility:** lead time (the slowest moved group, an assumption of parallel retooling) and minimum order quantity (exact unit match, no conversion) give feasible, infeasible or unknown, kept apart from the money. A known infeasible move or a fully priced negative net is demoted to the rejected rows with a reason, even when the other side is unknown; unknown money or unknown feasibility on its own never demotes. Cost never promotes a plan and never changes a legal result.
- **Money source and staleness:** an explicitly active `operations` block uses the request's whole economics even at an annual value of 0 (nothing priced, feasibility kept); otherwise the old rule (own economics with a positive annual value, else stored). A plan computed in the operating-cost mode records a hash of the raw money inputs (legacy plans do not); changing a cost, rate, constraint or the annual value makes the API mark the stored plan stale (a client must not present its money as current; the legal result and the money-free letter stay). Notes and sources change no result and no hash.
- **Not claimed:** no cost-optimal, cheapest, approved, legal or real-price claim; not modelled: capacity use, discounting and time value, taxes and residual value, ramp-up and yield, subsidies. Operating-cost plant entries are bound to the plant's name (or id when unnamed) and country, not a unique identity; the legacy `group_costs` table is still keyed by plant id, so #372 (a re-added plant inheriting an old group cost) is not fixed. Figures above 9e13 dollars become unknown (`arithmetic_range`); totals are sums of per-term cent-rounded values, so the two sides can differ from the net by a cent. Legacy golden tests compare parsed, normalised JSON, not raw HTTP bytes. Full description: `docs/modelled-operational-costs.md`.


## D137 — The public API: shared limits in production, per-client caps, security headers (21 Nov, review follow-up)
- **Why:** a review asked that the API given to the public have proper rate limiting and other security. An audit of main found: production counted limits per instance (deploy does not set `RATE_LIMIT_STORE`, so with up to 3 instances a client got about 3 times its limit); case reads, rename, delete, economics, export, demos, eval summary, workspaces and the duty-rate lookup had no limit, and the duty-rate lookup bypassed the shared counters; invalid API keys were unthrottled; no cap on concurrent model calls per client; only a global spend cap; no `RateLimit-*` headers; the HTTP server had only a header timeout; CSV uploads were parsed whole before any row cap; no security headers on the backend or the frontend.
- **Shared limits in production:** with `K_SERVICE` set, a project set and `RATE_LIMIT_STORE` unset, the store defaults to `firestore` (D70). If the Firestore client cannot be made at startup in that defaulted case, the instance starts with its own limits and logs a warning; an explicit `firestore` still fails startup. Each instance also deletes ended windows every 10 minutes (older than 5 minutes, 500 a batch, up to 10 batches), so `rate_limits` stays bounded with or without a TTL policy. The deploy workflow is unchanged.
- **Every route has a rate class:** a new `basic` class (120 a minute per client, `RATE_BASIC_PER_MIN`) covers the routes that make no model call, with a 30 s handler deadline. It is counted per instance only, not in Firestore, so a read costs no store write. A test fails if a `/v1` route is registered without `limit`, `rateOnly`, `cheap` or (admin routes only) `adminOnly`. The duty-rate live lookup now goes through the same path as ruling lookups (shared counters when configured).
- **Per-client caps:** at most 4 model-calling requests running at once per client on an instance (`RATE_MAX_IN_FLIGHT`; 429 `too_many_in_flight`, released when the handler returns, streams included); 10 invalid API keys a minute per address (`RATE_AUTH_FAILURES_PER_MIN`; then 429 `auth_rate_limited` before the key lookup); one client may spend at most a tenth of the daily model budget (`DAILY_SPEND_CLIENT_SHARE`; 429 `client_budget_reached`; admin exempt). Model calls are charged to the client through the request context; per-client totals are stored in `model_spend` under `<day>_c_<hash>`. If the API-key usage counter fails, requests are still served but counted on the instance, so a key stops at its quota there.
- **Headers:** limited responses carry `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`; the frontend proxy passes them and `Retry-After` through. Backend: `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on `/v1`. Frontend: HSTS, `nosniff`, `strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Permissions-Policy` (camera for this site only). The Content Security Policy is shipped as `Content-Security-Policy-Report-Only`: nonces would force per-request rendering, which `cacheComponents` rules out, and Google sign-in (scripts and frames from `accounts.google.com/gsi`) could not be exercised locally. No CORS headers are sent; cross-origin browser calls are not supported.
- **Server:** `ReadTimeout` 30 s, `IdleTimeout` 120 s, `MaxHeaderBytes` 64 KB beside the 10 s header timeout. No `WriteTimeout`, because predict and plan stream; a test shows a stream outlasting `ReadTimeout` keeps its context (Go 1.27).
- **Uploads:** CSV is read row by row with the sheet caps: 1,000 rows, 64 columns, and a new 2,000-character cap per cell for both formats.
- **MCP (#379):** `POST /mcp` takes the basic class (no deadline: a tool call may run a plan). Each tool call re-enters the handler chain in-process and takes its `/v1` route's limits there, so the in-flight cap, spend share, quota and failed-key limit apply once per tool call (tested). Security headers and `Cache-Control: no-store` cover `/mcp`; the frontend `/mcp` proxy passes the RateLimit fields through. In-process calls skip the `REQUIRE_BEARER` check (their POST was checked).
- **`REQUIRE_BEARER`** (default off): refuses requests other than `/health` without `Authorization: Bearer`. The frontend proxy always sends one on Cloud Run (`backend.ts`), and the deploy smoke test calls only the frontend, but whether Cloud Run passes the header to the container was not checked against the live service, so it stays off.
- **Checked, not changed:** the ruling and ask memos were already bounded (500 entries each). The 4xx messages that echo an error were spot-checked; none carried internals.
- **Measured:** unit and handler tests only (`internal/httpapi/api_security_test.go`, `internal/spend`, `internal/store` prune against the fake Firestore server, `internal/config`, `internal/bom`, `cmd/server`), and a local run with the fake model on ports 8183 and 3103: 429 after the basic limit with `RateLimit-*` and `Retry-After`, 429 `auth_rate_limited` on the 11th invalid key, the frontend security headers, and no CSP violation while moving through the main pages. Not run on Cloud Run or real Firestore.
- **Not done:** per-user (signed-in) limits are still per address or key; an invalid `X-User-Token` is not throttled like an invalid key; the in-flight and failed-key caps are per instance; no CSP enforcement; no Firestore TTL policy was created (owner action, below).
- **Owner action:** optional but cheaper than the prune: `gcloud firestore fields ttls update expires_at --collection-group=rate_limits --enable-ttl --project=<project>`.

## D163 — A second-stage adjudicator for the China component cluster: plan and pass rule, written before any run (21 Nov)
- **Why:** the largest error group on both held-out splits is CBP holding China (where the components or sub-assemblies were made) while the engine named the assembling country (13 of 37 misses on the 377, 4 of 6 on final2). A plain prompt rule for it lost on dev (D157). This tries a separate, focused second call instead, on the development split only first.
- **Stage 1** is unchanged engine-v1 on Gemini 4 Argon. The adjudicator reads the committed stage-1 rows of the production configuration and changes only the cases it is triggered on, so the comparison isolates the second stage (same stage-1 answers on both arms): dev `eval/results/dev-gemini-4-argon-prec-engine-v1-vertex.jsonl`; if it is ever scored on held-out, the 377 uses `final-gemini-4-argon-prec-engine-v1-vertex.jsonl` and final2 uses `final2-gemini-4-argon-prec-engine-v1-litellm-router.jsonl`. Adjudicator calls go through the gateway (D151) on Gemini 4 Argon, temperature 0, seed 20261017.
- **Adjudicator (`internal/adjudicate`, adjudicate-v1):** retrieves contrastive precedents dated strictly before the case, by BM25 on the facts: the closest earlier rulings whose facts name China and another country and where CBP held China, and the closest where CBP held the other, later-processing country. It shows the two candidate countries (China and the other one) without the engine's answer, and asks one question: is the processing outside China a substantial transformation of the Chinese components? Its answer replaces the engine's when it names one of the two candidates. A changed answer keeps the lower of the two confidences.
- **Variants, at most three:** (1) narrow: the engine named a country other than China, the facts name China, stated confidence below 0.96; (2) symmetric: the facts name China and another country and stated confidence below 0.95, whatever the engine named (the other candidate is the engine's answer, or the most-named non-China country when the engine said China); (3) chosen after (1) and (2), on dev only, and disclosed as chosen after them.
- **Pass rule on dev (463 after the D23 adjustments), against the stage-1 rows:** net fixed minus broke at least +5, exact McNemar p below 0.1, and total cost per case (stage 1 plus adjudicator) at most 1.5 times stage 1. ## D200 — Broker review loop: share one draft, get approve or changes back (21 Nov, review follow-up)
- **Why:** judge-panel item 12 (trade-compliance and design judges). Unde ended with "send a draft ruling request to your customs broker", but the product only offered a download, so the human check happened in email, outside the product.
- **Built:** the case owner makes a link for one draft (the current setup, or a plan picked as for export) with an expiry (default 14 days, at most 30) and can revoke it. The broker opens `/review#<token>` (the token is the URL fragment) without an account and reads a frozen snapshot: product, the prediction with calibrated confidence when a map applies, cited rulings, the plan, the draft letter, reviewer notes and the "not a ruling" disclaimer. The broker approves, requests changes (comment required) or marks it to file as a binding ruling request, and may answer again. The owner sees a status chip and a timeline on the case; MCP has `create_broker_review_link` and `get_broker_review_status`.
- **Storage:** links live inside the case document (no new collection, no Firestore index, every read by document id), so they are isolated, read and deleted with the case. The token carries the case id so the backend knows which document to read; only a SHA-256 of the whole token is stored and compared in constant time.
- **Snapshot, not a live view:** the broker approves exactly what the owner shared. A changed plan needs a new link. This also keeps the broker's routes from touching anything but the link's own record.
- **Security choices:** token only in the `X-Review-Token` header (never an API path or query), own rate class (`review`), invalid tokens limited like invalid API keys, 410 for revoked or expired links, noindex and no-referrer on the page and the API, comments stored as plain text and rendered as text, pinned demos cannot be shared out. Audit: `review.create` (fail-closed), `review.revoke`, `review.view`, `review.decision`; the broker is anonymous; no comment, token or case content in the trail. Details in docs/api/SECURITY.md.
- **Not done:** no broker account or identity check (whoever holds the link is the reviewer), no notifications, no edits to the letter by the broker, no e-filing (stays planned).
- **Token out of URLs that reach a server (coordinator review, same PR):** the first version put the token in the page path (`/review/<token>`), which Cloud Run's platform request log for the frontend records. The link is now `/review#<token>`: browsers never send a fragment to a server, so no request log or Referer holds it. The page reads `location.hash`, clears it with `history.replaceState` and keeps the token in memory only, so a reload or a bookmark cannot reopen the review (the page says to open the link again). `/review/<anything>` is a plain 404 that never reads the segment.

## D250 — Broker draft facts: line breaks, abbreviations and the comma rule (21 Nov, review follow-up, #434)
- **Why:** `export.CleanFacts` (D180) split paragraphs only on a blank `\n\n` line and sentences only on ". ". None of the 3,081 committed facts files uses `\n\n`; they use CR, CRLF, single LF or vertical-tab breaks. So a boilerplate sentence took the next paragraph with it (the heat gun's product description and testing step, with single LF or CRLF breaks), abbreviations left fragments ("Co. Inc.", "de C.V.."), the comma rule dropped a whole last paragraph, and the "never empty" fallback returned CBP's wording.
- **Built:** line breaks are normalised first (CRLF, CR, vertical tab, form feed to LF). A blank line, or a line break after the end of a sentence, starts a paragraph; a line break inside a sentence (a wrapped line, a date on its own line) does not. Sentences end at ".", "!" or "?" followed by a space and a capital, a digit or a quote, and at a period with no space before a capital ("ruling.The"). They do not end at a lower-case word, titles and references (No., e.g., i.e., Mr., Fig.), single initials (unless a usual sentence opening such as "The" follows), or company and place abbreviations followed by another abbreviation ("Mfg. Co. Inc.", "S.A. de C.V.") or by a noun after "U.S." ("U.S. Customs"). Only sentences with a boilerplate phrase are dropped; the comma rule drops only the last sentence when it ends in a comma. If nothing would be left, the facts come back with only the boilerplate removed; facts that are nothing but boilerplate give "[FILL IN: a description of the goods and how they are produced]."
- **Tests:** a table in `backend/internal/export/facts_test.go` covers every case in #434 (the abbreviation, trailing-comma and one-paragraph examples) and the heat-gun demo facts with LF LF, LF, CRLF CRLF, CRLF, CR CR and CR breaks in both letter formats. A corpus test runs over `backend/data/facts`: on the 2,613 files with a boilerplate phrase, no output keeps a phrase, no output paragraph starts with a fragment (it must start where the input starts a line or a sentence), and at least 99.5% of the other sentences are kept. The reference sentences come from a naive split after every end mark, so a piece of a dropped boilerplate sentence (cut at "Inc." or "U.S.") counts as lost: 32,973 of 33,046 kept (99.78%); the rest are those pieces, dangling comma fragments and the two limits below. The 468 files with no phrase keep their text, except one whose dangling comma fragment is dropped.
- **Before, same checks on the D180 function** (`git show e5a1737:backend/internal/export/facts.go`, run once, not committed): 49 outputs kept a phrase, 30 had a paragraph starting with a fragment, 32,399 of 33,046 reference sentences kept (98.04%), 48 outputs under half their input's length (6 now, all with a long boilerplate opening, or only boilerplate).
- **Limits:** a sentence that mixes a fact with a boilerplate phrase ("…in China or the U.S. and you have requested a determination for both") is dropped whole, as before. An abbreviation that ends a boilerplate sentence before an unusual opening can still join the next sentence to it (one corpus file: "…LLC. (LPA Korea) The merchandise…"). Single line breaks after a sentence now render as paragraphs.
