# Tenant-scoped audit trail (#284)

Scope: the backend. A separate, append-only, tenant-scoped trail of who did what, when, with what outcome. It is NOT the per-case `History` (a mutable, capped, per-case list of analysis steps). It is evidence that supports a broader SOC 2 readiness program. It is not a certification, an attestation, a compliance claim, or an immutable log (see section 8).

## 1. What exists today (inventory)

| Source | What it holds | Gap for audit |
| --- | --- | --- |
| Request log (`withRequestLog`) | method, route pattern, status, latency, request reference; no bodies | no actor, no tenant, short-lived log retention (Cloud Logging, outside this repo) |
| Case `History` (`store.Case.History`, `record()`) | up to 200 analysis events per case with the signed-in user's email as actor | mutable, trimmed, per case, holds email, nothing for denials, workspaces, API keys or deletes |
| `llm.WithLogging` | model call metadata (prompts at debug) | not an access record; redaction is #285 |

The audit trail fills the gaps: denials, deletes, workspace and role changes, API-key admin, exports, with a pseudonymous actor, and integrity checking.

## 2. Enablement

| Variable | Default | Meaning |
| --- | --- | --- |
| `AUDIT` | `auto` | `on`, `off`, `auto` (`true`/`1`/`false`/`0` accepted). `auto` is on only when `AUDIT_ACTOR_KEY` is set. `on` without the key is a startup error. |
| `AUDIT_ACTOR_KEY` | none | Secret, at least 32 bytes, from the operator's secret store. Never generated by the server, never logged, never in the trail. |
| `AUDIT_ACTOR_KEY_ID` | `1` | Key version stamped in pseudonyms. |
| `AUDIT_RETENTION_DAYS` | `90` | 1 to 3650. |
| `AUDIT_STORE` | follows `CASES_STORE` | `firestore`, `file`, `memory`. |
| `AUDIT_DIR` | `../data/audit` | file store directory; `off` selects memory. |

A deployment that does not set the secret keeps today's behaviour and the server logs `audit trail NOT enabled: no events are recorded and no audit evidence is produced`. In that state this document's controls are not in effect: there is no audit evidence to collect. Production never enables the trail by itself.

## 3. Event schema

One record per event, validated against closed enums and strict patterns before it is stored, so free text cannot reach the trail.

| Field | Values |
| --- | --- |
| `tenant` | `ws:ws_<12 hex>` workspace; `own:[u_\|key_]<32 hex>` personal tenant (the existing owner hash; only the admin token reads these); `platform` |
| `seq` | per-tenant, 1, 2, 3 ... assigned atomically |
| `time` | UTC, microsecond, never earlier than the previous event of the tenant |
| `actor_kind` / `actor` | `user` and `apikey`: pseudonym `a<keyid>_<32 hex>` (HMAC of the verified email or API key id under `AUDIT_ACTOR_KEY`); `admin` (one shared token), `anonymous`, `system`: no pseudonym |
| `target` | pseudonym of the affected member (invite, join, role, remove) |
| `action` | `case.create` `case.update` `case.export` `case.delete` `case.pin` `case.read` (denials only) `workspace.create` `workspace.invite` `workspace.join` `workspace.role_change` `workspace.member_remove` `workspace.leave` `workspace.retention` (#875, sensitive) `workspace.rename` (#870, sensitive) `apikey.issue` `apikey.list` `apikey.disable` `admin.watch_run` `audit.read` `audit.verify` `audit.export` (#871) `auth.denied` `review.create` `review.revoke` `review.view` `review.decision` (broker review links, D200) |
| `phase` / `outcome` | intent/allowed; completion/allowed or failed; single/allowed, denied or failed |
| `reason` | `forbidden` `hidden` `unauthenticated` `invalid_credential` `invalid_input` `conflict` `not_found` `upstream` `unavailable` `internal` `superseded` `audit_unavailable` `rate_limited` |
| `detail` | closed per action: update kind, export format, the new role, pin/unpin, the shared draft (`setup`, `plan`), the broker's decision (`approve`, `changes`, `file_request`) |
| `object` | `case:case_<hex>`, `workspace:ws_<hex>`, `apikey:<hex>`, `batch`, or `<kind>:h_<hex>` |
| `route` | the mux pattern, never the expanded path |
| `request_id` | the server's 16-hex id, or `h_` plus a hash of a client-supplied one |
| `ref` | on a completion, the `seq` of its intent |
| `suppressed` | denials dropped by the flood limiter since the previous event (per process) |
| `prev_hash`, `hash` | SHA-256 chain |

Never stored: emails, tokens, API keys or secrets, request bodies, facts, product, supplier or workspace names, display names, raw error text, an unverified visitor id. An id the requester supplied and the server did not resolve (a hidden or unknown case) is stored only as a keyed opaque hash.

## 4. Coverage

Every route registered in `server.go` has a row in `auditTable` (`internal/httpapi/audit.go`); `TestEveryRegisteredRouteHasAnAuditRow` fails for a route without one, as the isolation and role tables do.

| Route group | Events |
| --- | --- |
| Create (predict, batch, streamed predict) | intent, completion |
| Update (rename, economics, answers, scenarios, compare-targets, ask, watch, plan JSON and SSE, applied bom-version) | intent, completion |
| Export without `preview:true` | intent, completion |
| Export with `preview:true` on a private case | one `single/allowed` event (no history change; content leaves the system) |
| Delete case | intent (fail-closed), completion |
| Pin, watch run (admin token) | intent, completion |
| Workspace create | intent, completion |
| Invite, join, role change, remove, leave | intent (fail-closed), completion |
| API key issue, disable | intent (fail-closed), completion |
| API key list, audit read, audit verify | one `single/allowed` event |
| 401, 403, and a 404 that hid an existing case, on any audited route | one `single/denied` event in the requester's tenant |
| Invalid or expired user token or API key (middleware) | `auth.denied`, anonymous, `platform` tenant |
| Broker review link create (fail-closed), revoke, the broker's decision (D200) | intent, completion, in the case's tenant; the broker is `anonymous` |
| The broker reading a link | one `review.view` `single/allowed` event per read, in the case's tenant |
| Invalid, unknown, revoked or expired review token | `auth.denied`, anonymous, `platform` tenant |
| Allowed reads of a case, list, plan estimate | none (v1) |
| Stateless and public routes (`/v1/products/*`, rulings, eval, duty rates, demos, `/health`, `/v1/workspaces/mine`) | none |
| Pinned public demo analysis (nothing is saved) | none |
| SSO connection create, update, verify, delete (fail-closed); a connection list (#868) | intent, completion, in the workspace's tenant; the list is one `single` event |
| A finished SSO sign-in (#868) | one `sso.login` `single/allowed` event in the connection's workspace tenant, actor `anonymous`, the user as the pseudonymous target; `provisioned` when the sign-in made them a member. A refused sign-in is a denied `sso.login` in `platform` |

The trail is therefore NOT a complete record of who read confidential data: ordinary case reads are not recorded. It records writes, exports, deletes, administration and refusals.

Denials are recorded in the REQUESTER'S tenant, never the target's, so a caller cannot write into a chain they have no right to; an unverified visitor id (spoofable) never gets a tenant of its own and is recorded as `anonymous` in `platform`. One exception, by design: a broker holding a valid review link (D200) writes `review.view` and `review.decision` into the case's tenant as `anonymous`. The owner granted that access by making the link, and the token is checked before anything is written; an invalid, revoked or expired token never reaches the case's tenant. Auth middleware runs before any principal exists, so it records only a fact that needs none: a refused credential, with nothing the caller claimed.

## 5. Lifecycle and failure semantics

Order of an audited write: authorize, validate, intent, mutate, completion.

- Fail-closed (sensitive) actions: `case.delete`, `workspace.invite`, `workspace.join`, `workspace.role_change`, `workspace.member_remove`, `workspace.leave`, `apikey.issue`, `apikey.disable`, `review.create` (a link hands case content outside; revoking a link never waits on the trail), and the SSO connection changes `sso.connection_create`, `sso.connection_update` and `sso.connection_delete` (they decide who can sign in to a workspace, #868). If the intent cannot be stored the request is answered `503 audit_unavailable` and nothing is changed.
- Other writes: if the intent cannot be stored the write proceeds, is logged, and its completion has no `ref`.
- If the completion cannot be stored after the change, the change stands and the response keeps its real status. The status line is written after the completion attempt, so the response carries `X-Audit-Incomplete: completion-not-recorded`. The header can appear on any audit-enabled, non-streaming audited route, on a success or an error response: every mutating route, a recording or preview export of a non-pinned case, the audit read and verify routes and the API-key list. It is not limited to the fail-closed operations that can answer 503. An event stream commits its status before the work runs; it closes the audit explicitly before its final event, and if that write fails only a log line (request id, action, intent seq, error class) is possible. Either way the trail holds an intent with no completion (an allowed request that only writes a single event has no intent, so for it the header, or the log line on a stream, is the only sign; a failed denial event, such as a 401, 403, hidden 404 or invalid credential, sets no header and is only logged, or counted in `suppressed` when the flood limiter drops it).
- `verify` lists such intents (older than 5 minutes at the verification's start, no completion in the verified range) as unresolved. They mean: in doubt, the operation may or may not have happened. The list is AS OF `verified_through_seq`: a completion written after that point is outside the view, so an intent listed may already be closed now; run `verify` again. `complete:false` means the count is not exact.
- Completions are written at least once: a retried write whose first attempt actually landed can leave a duplicate completion for one intent. Read the unresolved list as 'no completion seen', not as 'exactly-once' accounting.
- Not atomic: the trail and the case, workspace or key stores are separate. No cross-store transaction is claimed. The Firestore adapter appends atomically per event (head and event in one transaction), but nothing spans the audit collection and the case collection. Tests for the memory and file stores do not validate Firestore.
- Denial and `single` writes are best effort; a failure is logged. A completion is tried at most twice (see at-least-once above); every other audit write once.
- Flood control: denials are limited per process (120/min per tenant, 30/min for `platform`, 600/min global, 256 tracked tenants, one shared overflow bucket) and the count of dropped ones is stored in `suppressed`. The limiter is per instance, in memory, and not a fleet-wide guarantee.

## 6. Access

`GET /v1/audit` (list) and `GET /v1/audit/verify`, registered only when the trail is on.

- The admin token, with `?tenant=` (required).
- A signed-in user whose current stored role in their workspace is admin, for that workspace; `?tenant=` from them is a 400.
- Everyone else: 403 (viewer, editor, user without a workspace, API key, visitor, nobody), or 401 under `STRICT_AUTH` for an unverified caller. Personal tenants have no tenant admin.
- Bounded: `limit` 1 to 200 (default 50), a scan of at most 1000 events per request, opaque cursors MAC-bound to tenant, order and every filter, unknown parameters rejected. Filters: action, outcome, phase, actor pseudonym, object, from/to. There is no filter by email.

## 7. Retention

`AUDIT_RETENTION_DAYS` (default 90). An in-process sweeper runs at start and every 6 hours and removes the oldest time-contiguous prefix of each tenant's chain in chunks, recording a checkpoint (`through_seq`, `through_hash`) first. `verify` anchors the retained suffix to the checkpoint, so a legitimate purge is not reported as tamper; a missing middle or a missing prefix with no checkpoint is. The head is never removed, so sequence numbers continue.

The audit collections do not use a Firestore TTL policy and none must be enabled on them: it would delete without a checkpoint and the gap would look like tampering. Retention of Cloud Logging is separate and unchanged.

## 8. Integrity: what it does and does not give

Verification works on a snapshot. The first call reads the head (seq and hash) and the retention checkpoint before any event, and the cursor carries them; events appended after that head are not part of the result (`verified_through_seq` says where it stops), so a live tenant does not look tampered and the `audit.verify` event written afterwards cannot extend the run. A retention purge that removes events a later page still needs makes the call answer `409 conflict` (start again without a cursor); it is never reported as a gap. A prefix removed without the checkpoint moving, a gap, a removed tail or a head that went backwards are still findings. Events past the frozen head are not part of the result, but the tail is checked against the LIVE head: the last call peeks one event past the snapshot and then re-reads the head; a real concurrent append moves the head with its event, so the head read afterwards reaches it, whereas an event the head does not reach (a head rolled back or edited down, a forged tail, an empty head over stored events) is a `head_mismatch`, at every page size. A verification cursor written before snapshots existed carries no frozen head and is refused with 400 (start again without a cursor). At most 100 findings are returned per call.

- Detects, with `verify`: a modified event, a reordered or inserted event, a deleted event in the middle, a removed tail (against the stored head), a missing prefix with no checkpoint, time going backwards, an event of another tenant.
- Does NOT give: immutability. The events, the head and the checkpoint are written by this application into one datastore. Whoever can write that datastore, a cloud administrator included, can rewrite all of them consistently and the chain will verify. There is no WORM storage, no external anchor, no signature by a key the datastore administrator lacks. Do not describe the trail as immutable or tamper-proof.
- Hardening not done here: anchoring the head hash in a separate system, object-lock storage, restricted IAM on the audit collections, backups. `GET /v1/audit/export` (section 13) gives the customer a copy and the head at that moment; keeping exports elsewhere is the customer's anchor, not ours.

## 9. Actor pseudonym key

A pseudonym is a keyed hash of a verified identity; it is not anonymisation, because whoever holds the key can confirm a guessed identity. Rotation: set a new `AUDIT_ACTOR_KEY` and bump `AUDIT_ACTOR_KEY_ID`; old events keep their pseudonyms and the chain stays valid; linking one person across a rotation needs the retained old key (keep it for the retention window). Cursors are keyed with the same secret, so a rotation invalidates outstanding cursors.

## 10. Evidence collection (what an operator or auditor can do)

1. Confirm the trail is on: startup log line `audit trail on` (store, retention, key id); absence of `audit trail NOT enabled`.
2. For a workspace: `GET /v1/audit?order=asc&limit=200` as its admin, or with the admin token and `?tenant=ws:<id>`; page with `next_cursor`.
3. Run `GET /v1/audit/verify` until `complete:true`; `ok:true` with no `findings`; read `unresolved_intents`.
4. Sample the coverage: perform a role change, a delete, a refused action and an export in a test workspace and find the events.
5. Retention: show `AUDIT_RETENTION_DAYS`, the `checkpoint` in the verify result after a sweep.
5a. Export (with `AUDIT_EXPORT=on`): `GET /v1/audit/export` as the workspace admin, then `go run ./cmd/auditverify export.jsonl` (exit 0 when intact).
6. Deployment items (NOT verified by this repository, require the cloud owner): the IAM members able to write or delete the audit collections, whether any Firestore TTL policy exists on them, the database backup and export policy, Cloud Logging retention, where `AUDIT_ACTOR_KEY` is stored and who can read it, and the current key id.

## 11. How this supports a SOC 2 readiness program

It produces evidence relevant to common criteria areas: logical access (who changed roles and members, who administered API keys), change and deletion of customer data, refused access attempts, and monitoring. It does not, by itself, establish any control as designed or operating effectively, does not cover reads, depends on the cloud controls in section 10 that are unverified here, and does not make the service SOC 2 certified or compliant. A SOC 2 report is an auditor's opinion over a period; this is one technical input.

## 12. Known low risks (recorded, not fixed here)

Firestore purge reads up to 400 oldest events per tenant per sweep and its cost is unmeasured; the file store uses mode 0644/0755 and follows symlinks (local development only); rotating `AUDIT_ACTOR_KEY` without bumping `AUDIT_ACTOR_KEY_ID` is not detected; a short `AUDIT_ACTOR_KEY` fails startup even with `AUDIT=off`.

## 13. Export (#871)

`AUDIT_EXPORT=on` (default off) registers `GET /v1/audit/export` with the same readers and tenant rules as `GET /v1/audit`. JSONL is the verifiable form: a `header` line with the head and retention checkpoint read before any event (a snapshot: later appends are not included), the events oldest first exactly as stored, and a `summary` line with the count and the SHA-256 of every byte before it. `cmd/auditverify` re-checks a file offline with the chain rules of `verify`; an export cut short by a store error has no summary and fails. `from` and `to` narrow by event time; such a file is checked event by event and link by link, not as a whole chain. CSV carries the same columns without header or summary. At most 200,000 events per export. Each export is an `audit.export` event in the tenant exported, written before the file streams. The same limits as section 8 apply: this is a copy the customer can keep, not a signature.

Case retention (#875, `RETENTION=on`) is separate from audit retention: a workspace admin sets `case_days` with `PUT /v1/workspaces/{id}/retention` (a sensitive `workspace.retention` write), and the operator's `cmd/retention -apply` purges expired cases, writing a tombstone and a system `case.delete` event (detail `retention`) before each deletion.
